## Research Process Recommendations

### What the prompt does well

1. **Editorial lens is precise and actionable.** The four relevance tiers with concrete examples (Sandcastle as "adaptable" even though it's API-based) give the agent real decision criteria. This is the prompt's biggest strength.
2. **Profile lookup procedure is thorough.** The five-step process with URL patterns and verification logic is good — the gap is not in the procedure but in its consistent application.
3. **Topic-by-topic research instruction** gives the agent a clear work order and prevents topic-level gaps.
4. **YouTube channel list is practical.** Maintained separately in `youtube_channels.json` and explicitly linked to the prompt.
5. **Scope guardrails are explicit.** "Do NOT include Sam Altman..." is clear and prevents noise.

### What's vague, missing, or could be more specific

**1. No definition of "research window" output format**

The prompt says "research the last 2 months of content" but doesn't say how to record what was checked. There's no `checked_sources` field, no "nothing found" signal. If HN yields nothing, there's no way to distinguish "checked and found nothing" from "skipped."

Suggestion: Add to the update log template a `sources_checked` section listing every source checked that run, even with "nothing new" entries.

**2. The profile-lookup procedure is not triggered consistently**

The prompt says "For each new or existing person who has 3+ null profile fields, run the profile lookup procedure." But 79% of people have 3+ null fields — meaning the profile lookup should be running for the entire registry every time. In practice it clearly did not run on the initial batch.

Suggestion: Add an explicit cap: "Run profile lookup for up to 5 existing people with the most null fields per weekly run, in addition to all new people." This prevents the task from becoming unbounded while making steady progress.

**3. The `github_stars` update cadence is undefined**

The prompt says to add tools with their star counts, but says nothing about updating star counts on subsequent runs. Star counts will drift immediately and become misleading.

Suggestion: Add to step 4 ("Find new tools/repos"): "Also update `github_stars` for any existing tools where the count in the description prose differs from the `github_stars` field — use the `github_stars` field as the single source of truth and remove inline counts from description text."

**4. Inline star counts in descriptions are not flagged as an anti-pattern**

10 tools have star counts in description text that now duplicate `github_stars`. There's no prompt instruction to avoid this.

Suggestion: Add to the "What to update" section: "For tools: put star counts in the `github_stars` field only. Do not mention star counts in the `description` text — they will become stale. Mention virality or momentum in prose form ('went viral', 'fastest-growing repos') without citing specific numbers."

**5. The `skills` and `design-tooling` topics are thin but the prompt doesn't prioritize them**

The prompt's topic list treats all topics equally. `design-tooling` has only 2 approaches documented and 1 person linked, but it's listed after multi-agent-orchestration with the same weight.

Suggestion: Add explicit notes next to thin topics: "design-tooling: under-researched, focus on finding new tools and practitioners specifically building design toolbars or Claude Code UI iteration workflows." The weekly update should know which topics need depth vs. which are well-covered.

**6. No instruction for handling duplicate event speakers**

The Brian Scanlan duplicate was caught in this audit. The prompt has no instruction to deduplicate `all_speakers` when adding event data.

Suggestion: Add to step 5 ("Find new events"): "When adding all_speakers, deduplicate by name — if a speaker appears in multiple tracks or sessions, list them once with the most prominent talk."

**7. No guidance on what to do with the `inbox.json`**

The prompt says to process inbox items first (step 0), but the two items currently in inbox.json (Open Design YouTube video, Caveman tool) remain unprocessed from the initial run. The prompt doesn't say what to do if an item was added after the research window was set.

Suggestion: Add: "Inbox items should always be processed regardless of the research window — they represent user-curated signals that take priority over the automated research."

**8. `author_id` on the article `latent-space-claude-code-launch` is semantically ambiguous**

This article lists `author_id: "shawn-wang"` but the content describes Boris Cherny and Cat Wu from Anthropic. swyx is the Latent Space publisher/host, not the content author of this episode writeup. For podcast transcripts/episode writeups, the `author_id` field is overloaded — it means "publisher" not "author."

Suggestion: Clarify in the prompt or schema: "For Latent Space episode writeups, `author_id` = the Latent Space author (swyx/Alessio). For How I AI episode writeups, `author_id` = Claire Vo. Use `guest_id` in podcast_episodes.json as the primary reference for the featured person."
